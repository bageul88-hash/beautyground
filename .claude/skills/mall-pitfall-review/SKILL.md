# 쇼핑몰 함정 감사

## 트리거
"쇼핑몰 함정 감사", "몰 코드 검토", "BG 함정 체크리스트", "함정 점검해줘"
자동 발동: `beautyground-mall` 또는 `buclockbeauty-mall` 저장소에서 UI·DB·결제·인증 관련 코드를 고친 뒤 커밋/배포 직전

---

## 한 줄 정의
이미 겪은 실수를 체크리스트로 박아두고, 새 코드가 그 실수를 또 반복하는지 커밋 전에 대조하는 규칙.

---

## 왜 필요한가 (해결하는 문제)
같은 실수가 뷰티그라운드몰과 뷰크라크에서 반복됐다 — RLS+GRANT 누락으로 로그인 회원이 몇 주간 주문·장바구니를 못 쓰던 사고(뷰크라크), 멀티브랜드 전제 로직이 단일브랜드몰에서 상품을 4개만 노출시킨 사고, PG 심사에서 "통신판매중개자" 템플릿 문구로 반려된 사고(뷰티그라운드몰). 항목이 18개나 되고 다른 세션·다른 작업자는 이 이력을 모르기 때문에, 사람이 매번 기억해서 챙기는 대신 체크리스트로 고정해 대조한다.

---

## 판단 기준 (18개 체크리스트)

### DB·보안
| 항목 | 확인 방법 | 실패 시 증상 |
|---|---|---|
| 새 테이블에 RLS는 있는데 GRANT가 빠졌는지 | `grant select/insert/update/delete on <table> to anon, authenticated;` + `NOTIFY pgrst, 'reload schema';` 실행 여부 확인 | 정책은 정상인데 401/403, 조용히 실패 |
| 결제금액을 클라이언트 값 그대로 믿는지 | 서버 코드가 DB의 실제 판매가로 재계산하는지 확인 | 가격 조작으로 고가 상품을 헐값에 구매 가능 |
| 관리자 라우트에 권한 게이트가 있는지 | 이메일 화이트리스트 / `is_admin()` 함수로 막혀있는지 | "로그인만 하면 관리자"가 되는 구멍 |

### 코드 재사용 (다른 몰 코드를 가져올 때)
| 항목 | 확인 방법 | 실패 시 증상 |
|---|---|---|
| 멀티브랜드 전제 로직이 단일브랜드몰에 숨어있는지 | "브랜드당 최대", "멀티브랜드" 키워드로 grep | 상품이 원래 수보다 훨씬 적게 노출 |
| 폐기된 디자인 월드 잔재가 새 컴포넌트에 복제되는지 | 확정 색상 토큰과 다른 구 컬러코드가 있는지 grep | 한 화면만 옛날 스타일로 붕 뜸 |
| 재가입 어뷰징 차단이 있는지 | 이메일/전화 키로 중복 수령 체크 테이블(`benefit_claims` 등) 존재 확인 | 매번 다른 이메일로 쿠폰만 계속 받아감 |

### CSS·디자인
| 항목 | 확인 방법 | 실패 시 증상 |
|---|---|---|
| tailwind 커스텀 재정의값이 있는지 | `tailwind.config.ts`에서 `rounded-xl` 등 기본값과 다르게 재정의된 게 없는지 확인 후 반영 | 기본값으로 착각해 디자인이 어긋남 |
| CSS 로드 순서로 유틸리티가 덮이는지 | 계산된 스타일만 보지 말고 **실제 화면 스크린샷**으로 확인 | 코드는 맞는데 화면에서만 깨짐(스크린샷 없이는 못 잡음) |
| hover 시 요소가 이동하는지 | translate/margin 변화로 커서가 벗어나는 애니메이션 있는지 확인 | hover가 붙었다 떨어졌다 진동 |
| sticky 헤더가 overflow 래퍼나 grid 안에 있는지 | 부모 요소에 `overflow`/`display:grid` 있는지 확인 | sticky가 먹통 |
| 모바일·PC 레이아웃 둘 다 반영했는지 | 두 레이아웃 파일 모두 diff에 포함됐는지 확인 | 한쪽만 고치고 다른 쪽 방치 |

### 계측·마케팅
| 항목 | 확인 방법 | 실패 시 증상 |
|---|---|---|
| 게스트→로그인 카트 병합 시 중복 집계되는지 | 병합 함수가 `silent` 등으로 트래킹을 건너뛰는지 확인 | 클릭 1번이 2건으로 집계 |
| 관리자 활동이 방문/이벤트로 집계되는지 | 관리자 경로(`/partner`, `/admin`) 제외 + `user_id` 판별 로직 확인 | 방문수·전환율이 실제보다 부풀려짐 |

### PG 심사·법적
| 항목 | 확인 방법 | 실패 시 증상 |
|---|---|---|
| "통신판매중개자" 등 템플릿 문구가 남아있는지 | 이용약관·개인정보처리방침 전체를 grep 전수확인(샘플링 금지) | 중개플랫폼으로 오인 → PG 심사 반려 |
| 사업자정보가 사업자등록증과 일치하는지 | 상호·사업자등록번호·통신판매신고번호·주소·대표자명 글자 하나까지 대조 | 심사 반려 |
| 옵션 상품이 제대로 등록됐는지 | 색상·호수·향 옵션이 있는데 단일 SKU인지 / 이미 옵션분리된 상품에 중복 옵션을 또 넣었는지 | 재고 없는 옵션 주문됨 |

### 인프라·운영
| 항목 | 확인 방법 | 실패 시 증상 |
|---|---|---|
| Vercel 함수 리전이 Supabase 리전(서울)과 맞는지 | `vercel.json`의 `regions` 확인 | 크로스리전 시 API 응답 최대 11배 지연 |
| 파일을 통째로 비우고 다시 쓰지 않았는지 + 저장소 편집 전 git fetch 했는지 | `open(path,'w')` 류 직접 사용 여부 / `git fetch`로 다른 세션 커밋 안 된 변경 확인 | 실패 시 원본 파일 유실 / 다른 세션 작업 덮어씀 |

## 실행 흐름
1. 점검 대상 범위 파악 — `git diff` 또는 최근 커밋 기준으로 바뀐 파일 목록 확보
2. 위 5개 카테고리를 순서대로 대조 — 각 항목은 grep/코드 확인으로 근거를 남긴다(추측 금지)
3. CSS·디자인 카테고리는 코드 확인만으로 끝내지 말고 **실제 화면(Playwright 등)으로 확인**
4. 걸리는 항목이 있으면 파일:라인과 함께 구체적으로 보고 — 수정할지는 대표님/작업자 확인 후 진행
5. 커밋/배포 직전이면 PG 심사·법적 카테고리는 반드시 전수 재확인(샘플링 금지)
6. 문제 없으면 "18개 항목 이상 없음"으로 짧게 보고, 있으면 항목별로 나열

---

## 역할 분담
이 스킬 자체가 "검토자" 역할이다. 구현(코드 작성)은 별도로 진행하고, 구현이 끝난 뒤 이 스킬로 대조만 한다. 하나의 세션이 구현과 검토를 순서대로 다 해도 되고, 규모가 크면 구현 담당과 별도 세션/에이전트로 나눠도 된다.

| 뷰크라크·뷰티그라운드몰 간 계정·설정 혼동 우려 | 즉시 중단 후 각 몰 전용 메모리(`reference_beaucrack_accounts.md` 등) 대조 |

## 🚫 절대 금지 규칙
1. **grep·코드 확인 없이 "문제없다"고 보고 금지** — 반드시 확인한 근거(파일:라인 또는 명령 결과)를 남긴다
2. **계산된 스타일만 보고 CSS 문제를 판단 금지** — hover 진동·CSS 로드순서 문제는 실제 화면(스크린샷)으로만 확인 가능
3. **PG 심사 직전 템플릿 문구 확인은 전수 grep으로만 — 샘플링(몇 페이지만 훑어보기) 금지**
4. **새로 발견된 실수를 그 자리에서만 고치고 체크리스트에 추가하지 않는 것 금지** — 다음에 똑같이 반복된다
5. **뷰크라크와 뷰티그라운드몰의 계정·사업자·설정을 섞어 쓰지 말 것** — 사업자가 다르면 PG·통신판매업 신고도 별개

## 주의사항
- 이 체크리스트는 **지금까지 발견된 것만** 담고 있다 — 완전하지 않다. 새 사고가 나면 즉시 이 파일에 항목을 추가할 것.
- 텍스트·카피 수정처럼 작은 변경에는 불필요하다. UI·DB·결제·인증 관련 변경에만 적용한다(과호출은 오히려 노이즈).
